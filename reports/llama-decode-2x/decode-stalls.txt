Intermittent decode stalls: ordinary Fusor transfer lowering
==========================================================

The 208-token prompt / 32-step throughput run stopped before the 256->512
KV-capacity boundary. A bounded one-layer fixture exposed 106-209 ms stalls
while ordinary tokens took approximately 0.5 ms. Capacity-dependent attention
and append code recompiled shaders, and migration used a new indexed-scatter
shader at each boundary.

The fix is in Fusor's regular GPU execution path, with no new profile flag or
cache-specific copy API:

- Contiguous range indices remain index expressions instead of opaque uploaded
  buffers. Ordinary padding, slice assignment, and cache migration retain that
  information through the normal logical graph and planner.
- The GPU backend lowers eligible Scatter{Set} and affine copy operations to
  standard WebGPU buffer copies/clears. It checks dtype, layouts, alignment,
  bounds, and aliasing, caps each transfer launch at 4096 regions, and retains
  compute lowering for unsupported layouts. Unused index producers disappear.
- Transfers preserve plan order, pool accounting, and compute timestamp indices.
  They use the existing command encoder, allocation budget, and submission path.
- Attention capacity, partition count, and append strides stay symbolic.
  Dispatch uniforms/grids change at growth; compiled decode kernels and the
  Llama decode graph remain reusable. KV allocation still grows incrementally.

Measured on Apple M2 Max, via WebGPU, with no GGUF or full-size model loaded:

  token    capacity        before ms / compiles     after ms / compiles
   65       64 -> 128       106.350 / 4                5.578 / 0
  129      128 -> 256       108.628 / 4                4.537 / 0
  257      256 -> 512       209.474 / 12               4.313 / 0

Steady median: 0.485 ms before, 0.514 ms after. Worst boundary: 209.474 ms
before, 5.578 ms after. This is a synthetic dense-weight one-layer fixture
using the real Llama forward/cache path, not a new full-model throughput claim.
The discarded cache-specific copy prototype is not the reported after result.

The regression asserts three growth boundaries, zero new boundary shaders,
and worst boundary below 100 ms and 20 times the steady median. Compile count
provides a deterministic check even when the driver's shader cache is warm.

Validation and reproduction
---------------------------

Use one compiler job; all tests below are explicitly ignored live-GPU tests.
No diagnostic optimization environment is required.

CARGO_BUILD_JOBS=1 cargo test -p kalosm-llama --lib \
  decode_latency_across_cache_growth --offline \
  --config profile.dev.opt-level=3 --config profile.dev.debug=0 \
  -- --ignored --nocapture --test-threads=1

CARGO_BUILD_JOBS=1 cargo test --manifest-path fusor/Cargo.toml --target-dir target \
  -p fusor-conformance --no-default-features --test contiguous_updates \
  --test inference_defaults --offline --config profile.dev.opt-level=3 \
  --config profile.dev.debug=0 \
  --config profile.dev.package.fusor-conformance.opt-level=0 \
  -- --ignored --nocapture --test-threads=1

The General-profile test uses plain Device::gpu(), checks exact padding and
nonzero slice assignment over five shapes, and requires zero compiled shaders
(before: five). It also checks preserved source values, compute roots, strided
updates, and the unaligned F16 fallback. Six existing forward/backward cases
run three deterministic shapes each: padding, slice assignment, concatenation,
repeat, and resize.

The nine numerical inference cases include a two-batch GQA attention graph
replayed through 256->512 storage growth and a changed partition count, checked
against host softmax attention. Existing NaN padding, tail, rotary, cache replay,
ring, and retained-snapshot checks also pass.

Core library/test Clippy, conformance Clippy, and all-target Llama Clippy pass
with warnings denied. CPU-only Llama compiles (five pre-existing unused host
profiling-variable warnings in the shared session code).

Compact measured boundaries, validation output, and process resource summaries
are in decode-stalls/. Raw local traces and build products are excluded.

  default-inference.txt
The original full-model memory guard was not loosened, and no full-model
benchmark was launched for this fix. Bounded synthetic checks ran serially
under a separate process-group guard. It stopped/refused checks when memory
headroom or the initial 1 GiB cap was exceeded; all owned groups were reaped.
Successful checks used a 1 GiB compiler/tiny-fixture cap or 2 GiB conformance
cap, reserved up to 3 GiB for process plus driver/cache allocations,
required at least 12 GiB remaining headroom, and allowed no added swapouts or
more than 32 MiB compressor growth. The conformance/release startup minimum
was 16 GiB. These are bounded test budgets, not permission to load an 8B model.

Release executable status: the normal fat-LTO chat rebuild reached linking,
then the guard stopped it at 2.0065 GiB process-group RSS, with no added swap
and 14.010 GiB system headroom. The owned group was reaped. A 3 GiB capped
link-only retry was refused at startup because available headroom had fallen
below 16 GiB; no further build was launched. The existing release executable
has not been replaced with this general-path revision. Rebuild the ordinary
chat command when memory headroom allows. No source build-profile or runtime
memory-limit settings were changed to bypass the guard.
